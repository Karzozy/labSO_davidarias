Punto 6. Lance un sleep 300 & y el shell me devolvio el PID 14427. Confirme con ps -ef | grep sleep que aparecia con ese mismo numero. Al consultar /proc/14427/status con grep -E 'Name|State|PPid|Threads' obtuve Name: sleep, State: S (sleeping), PPid: 3604, Threads: 1. El PPid (3604) coincide con el PID de mi shell que lanzo el proceso, tal como aparecia en la columna PPID de ps -ef. El State y el Threads no se ven en la salida normal de ps -ef, son datos extra que solo aparecen consultando directamente /proc.

Para lo de stat y wc, use /proc/self/status: stat -c %s /proc/self/status devolvio 0, y wc -c < /proc/self/status devolvio 1496. stat lee los metadatos del archivo tal como los reporta el sistema de archivos, y como /proc es un sistema de archivos virtual que no existe realmente en disco, el kernel no tiene forma de saber de antemano cuanto va a pesar el contenido, asi que reporta 0. wc en cambio si abre el archivo y cuenta byte por byte lo que realmente sale al leerlo, que se genera justo en ese momento con el estado actual del proceso que hace la lectura. Por eso los numeros no coinciden: uno pregunta por un dato que no existe, el otro mide el contenido real generado al vuelo.

Despues mate el proceso 14427 con kill 14427 y comprobe con ls /proc/14427 que la carpeta ya no existia, dando el error No such file or directory, y el shell confirmo con el mensaje Terminated. Esto confirma que /proc no guarda nada, solo muestra lo que hay vivo en ese momento.

Punto 8. Empezando por mi propio shell, PID 13898 obtenido con echo $$, fui consultando el PPid de cada proceso uno por uno. La cadena quedo asi: bash 13898 tiene PPid 13867, que es su, y su 13867 tiene PPid 13701, que es otro bash, y ese bash 13701 tiene PPid 13694, que es gnome-terminal, y gnome-terminal 13694 tiene PPid 1726, que es systemd, y ese systemd 1726 tiene PPid 1, que es el proceso 1, tambien systemd, cuyo PPid es 0. El proceso 1 es el unico cuyo PPid vale 0, porque no tiene padre: es el primer proceso que arranca el kernel al iniciar el sistema. En mi maquina ese proceso es systemd. Todo lo demas, en algun punto de la cadena, termina colgando de el. El su aparece en la cadena porque fue el comando que use para cambiar a mi otro usuario.

Punto 22. Corri ./infoproc.sh 12340 y ./infoproc 12340 sobre el mismo proceso, que era Firefox, y la informacion salio identica en ambos: PID 12340 firefox-esr en estado sleeping con PPid 11684 y 140 hilos, PID 11684 gnome-shell en estado running con PPid 1726 y 43 hilos, PID 1726 systemd en estado sleeping con PPid 1 y 1 hilo. Tiene sentido porque, aunque estan escritos en lenguajes distintos y usan mecanismos distintos para leer, el script usa el read de bash y el programa en C usa open, read y close directamente, al final los dos estan leyendo el mismo archivo, /proc/PID/status, que genera el kernel en el momento de la consulta. No importa como se lea, la fuente de la informacion es siempre la misma, asi que el resultado tiene que coincidir.

Punto 23. Corri ./infoproc.sh 12340 tres veces seguidas sobre Firefox y la cantidad de hilos cambio en cada corrida: 139, luego 141, luego 140. El estado se mantuvo en sleeping las tres veces, pero el numero de hilos si vario. Con procesos quietos como systemd o sleep esto no pasa, siempre dan el mismo valor. Tiene sentido porque Firefox esta todo el tiempo creando y cerrando hilos para distintas tareas, como red o renderizado, asi que cada vez que uno consulta /proc esta viendo una foto distinta de un proceso que nunca deja de moverse.

Punto 24. Cuando escribo algo en la terminal y doy Enter, el shell primero lee esa linea y separa el comando de sus argumentos. Si es algo que el shell resuelve por si mismo, como cd, lo hace ahi mismo sin crear nada nuevo. Pero si es un programa externo, el shell se clona a si mismo con fork, que crea un proceso hijo identico a el, y ese hijo usa exec para convertirse en el programa que pedi, sin dejar de ser el mismo proceso en terminos de PID. Mientras tanto el shell original se queda esperando con wait a que ese hijo termine, y solo cuando termina vuelve a mostrarme el simbolo de que esta listo para el siguiente comando. Si mando el proceso a segundo plano con el signo &, el shell no se queda esperando, me devuelve el control de una, pero sigue llevando la cuenta del proceso por si termina despues, por eso aparecieron esos mensajes de Done cuando el sleep termino solo, y Terminated cuando lo mate con kill.

Otras cosas que anote. infoproc.c compila sin ninguna advertencia con gcc -Wall -o infoproc infoproc.c. Probe el caso de un PID que no existe en los dos programas, con ./infoproc.sh 999999 y ./infoproc 99999999, y ambos avisan que el proceso no existe y terminan con codigo de salida 1, verificado con echo $?. El script convertir.sh lo corri dos veces seguidas sobre la carpeta prueba_videos, que tenia cuatro archivos: clase1.mkv, clase.2026.2.mkv, clase.2026.3.mkv y clase.2026.4.mkv. La primera vez convirtio los cuatro, mostrando Convertidos 4 y Saltados 0, la segunda no convirtio ninguno, solo informo que los estaba saltando porque el mp4 ya existia, mostrando Convertidos 0 y Saltados 4. El archivo clase.2026.2.mkv, que tiene varios puntos en el nombre, se convirtio correctamente en clase.2026.2.mp4, confirmando que el operador de patrones que usa el script recorta solo la extension final y no cualquier otra parte del nombre.
